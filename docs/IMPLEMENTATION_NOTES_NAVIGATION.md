# Implementation notes — mouse navigation and automatic interaction

This note records the decisions behind the mouse-navigation round: what was added,
what was deliberately not added, how it is proven, and what is still unverified.

The rules themselves live in `docs/ARCHITECTURE.md` §5f. This file is the
reasoning and the evidence.

## 1. What the player can now do

- **Click the floor** and the character walks there along the location's navigation
  mesh. A quiet ring marks the destination and clears when the walk ends.
- **Click a person, a prop or a door** and the character walks to a spot inside that
  object's interaction radius and uses it on arrival. Clicking something already
  within reach uses it immediately, without a step.
- **Keep using the keyboard.** WASD/arrows still walk, and holding any of them during
  an automatic walk takes over. **E** still activates the highlighted object without
  moving. The mouse is an addition, not a replacement.

## 2. The three rules that keep it honest

1. **One movement implementation.** `PlayerController._apply_movement()` is the only
   place velocity is written. Path following does not get its own acceleration,
   gravity or collision handling; it only supplies a direction.
2. **One activation path.** Automatic interaction calls
   `InteractionController.request_activation()`, exactly what E calls. A clicked door
   goes through the same director, the same beat lock and the same transition as a
   pressed one. The navigation code contains no dialogue, transition or story logic.
3. **Nothing is faked.** No teleport is used to reach a destination, no straight-line
   shortcut is taken through furniture, and no test asserts a walk that did not
   happen. Where a walk is impossible the request is refused (off the mesh, no route,
   control locked) or abandoned (target gone, disabled, out of reach, stalled).

## 3. Decisions worth recording

- **Runtime baking over stored meshes.** Each location bakes its own
  `NavigationMesh` from its own static colliders when it loads
  (`scripts/world/location_navigation.gd`). Four of the six locations are generated by
  `tools/build_outdoor_locations.py`, so a stored mesh would silently go stale the
  first time a box moved. A failed bake is visible: `get_polygon_count() == 0` and the
  navigation test fails that location by name.
- **The component collects its own geometry.** `LocationNavigation` walks the location
  tree itself and hands every `StaticBody3D` on the world layer to the baker, rather
  than calling the engine's source-geometry parser. The furniture in a greybox room is
  an instanced prop two or three nodes down, and when those bodies were left out the
  bake produced a single floor plate: the mesh promised a route through the desks, and
  the body ground against them halfway across the room. `get_geometry_face_count()`
  makes the difference visible in a log.
- **A baked mesh is not a working map.** The navigation server takes a region's
  polygons a frame or two after the bake, and a query in that window answers with the
  zero vector — which reads as "the spawn is 14 m off its own floor". The component
  exposes `is_routable()` (it asks the map for a real route) and re-hands the mesh over
  once if the polygons did not arrive; the tests wait for it instead of for
  `is_baked()`.
- **The route is followed by the body, not by the agent's index.** The walk keeps the
  path the map returned and drops each corner it reaches. Asking `NavigationAgent3D`
  for the next path position each frame reads a path index the server updates on its own
  step, which lags the body; with a long physics step the character rocked between two
  corners it had already passed, for as long as the walk was allowed to last.
- **The body climbs a kerb, and the mesh agrees.** `CharacterBody3D` treats every box
  as a wall, so a 15–28 cm kerb stopped the character dead while the mesh (with a
  0.4 m climb) promised it was walkable. `PlayerController.max_step_height` (0.3 m)
  lifts the body onto low steps only — a desk or a wall still stops it — and
  `agent_max_climb` is set to the same 0.3 m so the two cannot disagree again.
- **The street's way back is its own key.** `prompt.back_to_classroom`
  ("Return to classroom" / "回到教室") on `street_back_to_school` only; the corridor's
  door keeps `prompt.back_inside` ("Go back inside" / "回到里面"). The destination,
  spawn and transition are untouched.
- **The dismissal rewrite was narrowed.** `OpeningSequence._update_exit_prompt()` used
  to rewrite every exit whose destination was the corridor. Once the street existed
  that also matched the street's return exit, so standing in the street at the school
  door showed "Leave the classroom". It now rewrites only the exit whose `interact_id`
  is `classroom_door`.
- **Arrival is measured, not assumed.** `arrival_radius` (0.45 m) ends a walk; a stall
  watchdog (2 s without progress) ends a walk that cannot progress, instead of letting
  it push into a wall forever.
- **A click a `Control` consumed never reaches the world.** The navigator listens on
  `_unhandled_input`. The tests count the mouse presses that actually arrive as
  unhandled input, and check that counter against a control case, so "no leak" cannot
  be true by accident.

## 4. Not in this round

- No dialogue-panel redesign, no NPC name labels, no new character models, no story or
  dialogue rewrites, no minimap, no combat, inventory or quests, no camera or location
  rebuild, no third-party navigation addon, no wholesale rewrite of the player or of
  the interaction controller.
- No agent avoidance between moving bodies, no off-mesh links for stairs that are not
  ramps, no path smoothing, and no navigation-aware companion. Each mesh covers one
  location only, so nothing routes across a boundary.

## 5. Evidence, and what it is not

Automated (headless, CI):

- `tests/navigation_test.gd` — per-location bake, spawn coverage and spawn→exit
  reachability; a real walk with the physics body (arrival, distance travelled, no
  drift afterwards); refusal of off-mesh points; an unreachable island that is never
  climbed; a wall added between the player and the destination that is walked around
  (waypoint count and clearance measured); manual cancellation; destination
  replacement; cancellation across a location swap.
- `tests/automatic_interaction_test.gd` — click-to-talk from across the room,
  immediate activation in reach, an inspectable prop, a probe exit whose transition
  runs through the director, a target disabled mid-walk, a target freed mid-walk,
  E still working, and a ground click that moves without activating anything.
- `tests/dialogue_pointer_test.gd` — one option per click, no fall-through to the
  world (against a control case), digit keys, hover styling, layer order, and a
  language switch that re-renders the options in place.
- `tests/street_prompt_test.gd` — the new prompt key in both languages, the unchanged
  destination, the corridor's separate key, and the dismissal rewrite leaving the
  street alone.

Visual (capture workflow, scripted, not a human playtest):

- floor click → destination ring → visible movement, with the route's waypoint count
  and length logged beside the straight-line distance;
- a held movement key interrupting an automatic walk;
- a click on the timetable sheet opening its inspection;
- a click on Q from out of reach: the walk, then the conversation;
- a click on the classroom door: the transition without a key;
- a mouse-selected dialogue option in the residential stair conversation.

Both CI jobs pass on the branch head: the Godot CI job (24 headless checks, the four
new ones included) and the playthrough capture job, which reports `RESULT: the
playthrough reached the end of the built content.` and writes the frames.

The game code was red for seven rounds before that, and every failure turned out to be
a defect rather than a test to relax. The three that were invisible from reading the
code:

- a navigation region whose cell dimensions disagree with the map is refused silently,
  and the map only answers queries a frame or two after the bake — `is_routable()`
  exists because a mesh can be perfect and the map still empty;
- a headless run opens a 64×64 window, so a bottom-anchored panel is laid out above the
  top edge and a click on one of its buttons lands outside the viewport;
- the engine's source-geometry parser did not pick up the instanced prop bodies, so the
  classroom baked a floor plate with every desk left out.

The capture went red six more times with the game code untouched, and every one of those
was the capture's own brittleness:

- a step written under GitHub's `-e` threw its log away at the first non-zero exit, so a
  failure arrived as "Process completed with exit code 1" and nothing else;
- the floor-click scan reached down to 85% of the viewport height, inside the
  bottom-anchored dialogue panel, so a point picked there was a click on the panel;
- the same scan asked for floor 4–6.5 m away with no fallback, and at one classroom spot
  found none — which was then reported as "a click did not move the character";
- a clicked point can sit on visible floor the map cannot reach. The navigator builds a
  route to the nearest point it *can* reach, the character takes two steps, and the
  capture read that as a walk that did not happen;
- teleporting to a starting position can leave the capsule inside a desk. The map still
  answers, the walk starts, `move_and_slide()` has nowhere to go, and the stall watchdog
  cancels it — three attempts, each 0.00 m from where it started;
- the engine can exit non-zero under Xvfb while tearing down the window and GL context,
  after the run wrote `RESULT` and printed no failure, which failed a playthrough that
  had finished.

That last one changed what the capture job trusts. The log decides now: a `FAILURE:`
line fails the job, and so does a missing `RESULT` marker; a non-zero exit after a clean
marker is reported as a warning about teardown instead. A run that stops early still has
no marker and still fails, so the bar has not moved.

The capture has not been run on Windows, and no hands-on playtest has been performed
on any platform. The Windows checklist for a human is in the pull request.
