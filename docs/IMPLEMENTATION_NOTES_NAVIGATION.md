# Implementation notes — mouse navigation and automatic interaction

This note records the decisions behind the mouse-navigation round: what was added,
what was deliberately not added, how it is proven, and what is still unverified.

The rules themselves live in `docs/ARCHITECTURE.md` §5f. This file is the
reasoning and the evidence.

## 1. What the player can now do

- **Click the floor** and the character walks there along the location's navigation
  mesh. The click ripples once where it landed and leaves a quiet ring that turns and
  breathes while the character walks; the ring collapses and fades when the walk ends.
- **Click a person, a prop or a door** and the character walks to a spot inside that
  object's interaction radius and uses it on arrival. Clicking something already
  within reach uses it immediately, without a step.
- **Hear the click land.** Every one of those clicks answers in the ears as well as on the
  floor: a soft tick where a walk was accepted, the same tick a little brighter on an object,
  a closed thud when the world refuses, and a very quiet tick when the pointer finds something
  it can use. The sounds are synthesised in the code and sit under the room tone.
- **Keep using the keyboard.** WASD/arrows still walk, and holding any of them during
  an automatic walk takes over. **E** still activates the highlighted object without
  moving. The mouse is an addition, not a replacement.

## 2. The three rules that keep it honest

1. **One movement implementation.** `PlayerController._apply_movement()` is the only
   place velocity is written. Path following does not get its own acceleration,
   gravity or collision handling; it only supplies a direction.
2. **One activation path.** Automatic interaction calls
   `InteractionController.request_activation()`, exactly what E calls. A clicked door
   goes through the same director, the same beat lock and the same transition as a
   pressed one. The navigation code contains no dialogue, transition or story logic.
3. **Nothing is faked.** No teleport is used to reach a destination, no straight-line
   shortcut is taken through furniture, and no test asserts a walk that did not
   happen. Where a walk is impossible the request is refused (off the mesh, no route,
   control locked) or abandoned (target gone, disabled, out of reach, stalled).

## 3. Decisions worth recording

- **Runtime baking over stored meshes.** Each location bakes its own
  `NavigationMesh` from its own static colliders when it loads
  (`scripts/world/location_navigation.gd`). Four of the six locations are generated by
  `tools/build_outdoor_locations.py`, so a stored mesh would silently go stale the
  first time a box moved. A failed bake is visible: `get_polygon_count() == 0` and the
  navigation test fails that location by name.
- **The component collects its own geometry.** `LocationNavigation` walks the location
  tree itself and hands every `StaticBody3D` on the world layer to the baker, rather
  than calling the engine's source-geometry parser. The furniture in a greybox room is
  an instanced prop two or three nodes down, and when those bodies were left out the
  bake produced a single floor plate: the mesh promised a route through the desks, and
  the body ground against them halfway across the room. `get_geometry_face_count()`
  makes the difference visible in a log.
- **A baked mesh is not a working map.** The navigation server takes a region's
  polygons a frame or two after the bake, and a query in that window answers with the
  zero vector — which reads as "the spawn is 14 m off its own floor". The component
  exposes `is_routable()` (it asks the map for a real route) and re-hands the mesh over
  once if the polygons did not arrive; the tests wait for it instead of for
  `is_baked()`.
- **The route is followed by the body, not by the agent's index.** The walk keeps the
  path the map returned and drops each corner it reaches. Asking `NavigationAgent3D`
  for the next path position each frame reads a path index the server updates on its own
  step, which lags the body; with a long physics step the character rocked between two
  corners it had already passed, for as long as the walk was allowed to last.
- **The body climbs a kerb, and the mesh agrees.** `CharacterBody3D` treats every box
  as a wall, so a 15–28 cm kerb stopped the character dead while the mesh (with a
  0.4 m climb) promised it was walkable. `PlayerController.max_step_height` (0.3 m)
  lifts the body onto low steps only — a desk or a wall still stops it — and
  `agent_max_climb` is set to the same 0.3 m so the two cannot disagree again.
- **The street's way back is its own key.** `prompt.back_to_classroom`
  ("Return to classroom" / "回到教室") on `street_back_to_school` only; the corridor's
  door keeps `prompt.back_inside` ("Go back inside" / "回到里面"). The destination,
  spawn and transition are untouched.
- **The dismissal rewrite was narrowed.** `OpeningSequence._update_exit_prompt()` used
  to rewrite every exit whose destination was the corridor. Once the street existed
  that also matched the street's return exit, so standing in the street at the school
  door showed "Leave the classroom". It now rewrites only the exit whose `interact_id`
  is `classroom_door`.
- **Arrival is measured, not assumed.** `arrival_radius` (0.45 m) ends a walk; a stall
  watchdog (2 s without progress) ends a walk that cannot progress, instead of letting
  it push into a wall forever.
- **A click a `Control` consumed never reaches the world.** The navigator listens on
  `_unhandled_input`. The tests count the mouse presses that actually arrive as
  unhandled input, and check that counter against a control case, so "no leak" cannot
  be true by accident.

## 4. The cue round: what the mouse draws

The first version of the cues was two hand-rolled tori — one flat ring on the highlighted
object, one flat ring at the destination — and they looked like what they were: three
days of code that nobody had looked at on a screen. What was wrong with them, in order:

1. **A solid glowing hoop is the most generic mark in a 3D game.** The object ring also sat
   at a fixed radius regardless of the object, so a door and a schoolbag got the same ring,
   and neither told the player where to *stand*.
2. **Nothing moved.** Both rings were switched on and off between two frames, which reads
   as a rendering fault rather than as the game pointing at something.
3. **The two rings shared nothing.** Different colours, different thickness, different
   emission: an object saying "use me" and a floor saying "walk here" looked like two
   different tools made by two different people.
4. **The refusal was a dimmer version of the acceptance.** Same shape, same direction,
   weaker colour — so the cue that promised a walk and the cue that refused one differed by
   a shade of brightness.
5. **The ring was always horizontal**, so on a kerb or a ramp it floated on one edge.

`scripts/interaction/world_cue.gd` answers 1 and 3: one palette, one pen width, one dash
rhythm, one unshaded material per role, every mesh built from code with `SurfaceTool`. The
roles are words (`destination`, `target`, `refused`) rather than colours at the call site,
because the role is the decision and the colour is only how it is drawn.

`scripts/interaction/hover_cue.gd` answers 1 and 2 for the object: a dashed ground ring
whose radius is derived from the interaction radius (the ring marks where the player has to
stand, so it has to agree with the reach test) and which `Interactable` projects down onto
the floor with one ray — interactables are authored at the middle of the prop, so their own
height is not the ground — a wider halo breathing out of step with it,
and a small shard tumbling above the object — which keeps the cue legible when the prop
stands on a shelf, in a doorway or behind a desk, where a ground ring is hidden. All three
parts fade in over 0.14 s and fade out over 0.16 s.

`scripts/interaction/destination_cue.gd` answers 2 and 4 for the click: the accepted click
ripples outwards once (the gesture of a click landing), leaves a ring that turns and
breathes for as long as the walk lasts, and collapses when the walk ends. The refused click
*collapses inward* with two flicks instead of expanding, because direction is what carries
the meaning: outward is a promise, inward is a withdrawal. It ends itself after 0.55 s —
a refusal is not something the player has to dismiss.

Point 5 is one ray, cast only when a click is accepted or refused, against the ground layer:
the hit normal orients the cue. A flat ring on a slope floats on one side and sinks on the
other, which is the kind of detail that makes an effect look broken without anyone being
able to say why.

Two things were deliberately *not* done:

- **The clicked prop is not lit while the character walks to it.** It would have been the
  obvious Disco-Elysium-ish move, and it would have broken the rule that exactly one
  object is highlighted and it is the one E uses: `InteractionController` owns the
  highlight, and a second owner would have made the cue and the key disagree. The walk is
  drawn in the *target* colour at the spot it ends on instead — the same information,
  attributed to the same object, with one owner.
- **No cursor replacement and no world-space prompt text.** Both are real Disco Elysium
  affordances, and both need art and a font pass the project does not have yet. The prompt
  keeps its text and gains a 0.12 s fade; nothing was invented to fill the gap.

Evidence: `tests/interaction_cue_test.gd` (headless: parts, motion, roles, ground
alignment, self-dismissal, radius follows the interaction radius) and
`tests/interaction_audio_test.gd` (the same cues as sound: buffers, levels, the hover rate
limit, silence, and that the drawing code asks for the matching cue) plus three capture frames
— `03a_click_destination`, the new `03d_hover_cue` (real cursor on the timetable sheet) and
`03g_refused_click` (a click on a wall). What a headless test cannot prove is what the
cues *look* like; that is what the frames are for, and a human pass on Windows is still
listed in the pull request.

### The cue has a voice

The shapes answer "did that register, and where"; they do not answer it when the player is
looking somewhere else on the screen, which is most of the time. A click is now
acknowledged in the ears as well:

| cue | sound | level |
|---|---|---|
| destination (floor) | 430 Hz dry tick, 0.15 s | −20 dB |
| target (object) | 575 Hz, the same tick a little brighter | −20 dB |
| refused | 138 Hz closed thud with a noise floor, 0.24 s | −22 dB |
| hover | 1180 Hz tick, 0.045 s | −30 dB |

Choices worth writing down:

- **Nothing is a file.** `scripts/audio/cue_audio.gd` computes the four buffers at startup
  with the same additive synthesis `tools/generate_placeholder_audio.py` uses for the room
  tones. No sample library, no `.import` sidecar, no licence row to maintain — the same
  reason the cues are drawn with `SurfaceTool` instead of authored meshes. The refusal's noise
  is a seeded integer sequence, so the bytes are identical on every machine, which is what
  lets a test assert on peaks at all.
- **The role decides both senses.** `PointerNavigator` calls `_announce(role)` before it draws
  the shape of that role, and `Interactable` ticks when it becomes the highlighted object. No
  third piece of code decides that a refusal is "bad", so the picture and the sound cannot
  drift apart.
- **Only the hover tick is rate-limited** (one per 0.12 s). It fires whenever the highlighted
  object changes, which happens as the pointer sweeps a room; the three click sounds are not
  limited, because a click is always worth hearing and a player cannot produce two in ten
  milliseconds. Two voices per sound let a second click play beside the first instead of
  cutting it off.
- **The sounds sit under the room tone**, at −20 … −30 dB, with the refusal the quietest of
  the three clicks. A cue is an acknowledgement, not an event; the school bell stays the
  loudest thing in the scene.
- **Silence is a first-class state.** `set_silent()` exists for the settings screen that does
  not exist yet, and a muted cue is not counted, because the counter is meant to mean "heard".
  A headless run that registered no autoloads finds no `CueAudio` node and plays nothing
  rather than failing.

A sound cannot be photographed, so the capture run writes the counts into its log
(`cue audio after the mouse shots: {…}`) — a real click through the real input system has to
move those numbers, and that is the only evidence a headless CI can carry for audio.

### The frames, and why there had been none

Chasing the first frame list turned up something older than this round. `capture_playthrough.gd`
extends `SceneTree`, so `get_tree()` does not exist inside it — and one helper called
`await get_tree().physics_frame`. That is a parse error, so the script failed to *load*:
every capture run produced nothing at all, while the workflow reported success, because the
evidence folder was filled by copying `docs/screenshots/` wholesale and that folder still
held the previous run's `PLAYTHROUGH.log` with its `RESULT:` line. Two runs fourteen minutes
apart quoted the same log line, which is how it was finally caught.

Three small guards, all in the capture path rather than in the game:

- Files are staged only if they were written *after* a stamp taken at the start of the run;
  a run that produced nothing has nothing to read a verdict from and fails.
- The capture script is compiled by the test workflow (`--check-only`), so a script no test
  loads cannot sit in the tree broken again.
- The prompt shots stand where the prop actually is (`_position_near`) instead of at a
  hardcoded coordinate that faced it when the shot was written.

The first full run after those fixes produced 46 in-game frames plus the UI and editor sets,
and it is that run that `03a`/`03d`/`03g` above come from.

## 4b. The bake, measured (added in Phase 5b.3)

The bake was already the expensive part of entering a location; what was missing was any
way to know how expensive. `LocationNavigation` now measures itself, once per bake:

| Question | Answered by |
|---|---|
| how long did the bake take, and how much of that was geometry collection? | `get_bake_usec()`, `get_collect_usec()` |
| how much geometry went in? | `get_geometry_face_count()` — collision faces parsed from every `StaticBody3D` on the world layer |
| how much walkable surface came out? | `get_polygon_count()` — polygons in the baked mesh |
| did the map take it? | `get_map_region_count()`, `is_routable()` |
| why did it fail? | `get_bake_error()` |

Nothing here runs per frame: the numbers are written once, inside `bake_region()`, and a
debug build prints one line (`LocationNavigation: '<scene>' baked in X ms (collect Y), N
faces -> M polygons, K region(s)`). Release builds print nothing.

**What the measurement exposed.** Not a slow bake — a *missing* one. The pressure test kept
finding a room whose mesh was correct (`polygons` right, `faces` right, region on the map)
and whose map could not answer a single route, and only sometimes: the corridor, on the
frame the player arrived.

The cause is the server's schedule, not the geometry. The navigation server parses a
region's mesh and rebuilds its map on its own schedule. A map that has not rebuilt yet
answers queries from the polygons it still holds, and right after a location swap what it
holds is the room that has just been freed. So `is_routable()` said *yes* about a floor that
was about to disappear, and once it had gone, the new room's polygons were in the mesh and
not yet in the map. For a player that is a room where click-to-move quietly falls back to
"the nearest point I can reach", which may be two metres away and in the previous room.

Two changes, one diagnostic:

- `map_knows_geometry()` answers the question `is_routable()` cannot: the closest walkable
  point to a corner of *this* mesh has to be that corner. A map holding another room's floor
  fails it by the distance between the two rooms.
- `_verify_baked_geometry()` runs on the frames after a bake, hands the mesh over again while
  the map still answers for something else, and stops after `ROUTE_RECHECK_FRAMES` (6) with
  a recorded `_bake_error` rather than pretending. It costs nothing when the map keeps up,
  which is almost always.
- The bake also duplicates the authored `navigation_mesh` instead of writing into it, because
  a `.tscn` shares its sub-resources between instances and a per-instance bake must not write
  into a shared one. It is a safety measure today — none of the shipped location scenes
  authors a mesh, so they all bake into a fresh `NavigationMesh` already — and it exists so
  that the first scene that does author one cannot poison another instance.

**What the pressure test does with it** (`tests/location_pressure_test.gd`): enters all six
locations, asserts for each that the navigation really baked (faces > 0, polygons > 0, a
region on the map, a measured duration, and a non-zero share for collection), that the room
around the spawn is walkable — eight directions at four metres, at least three arriving —
and that spawn-to-spawn pairs which are *not* routable are reported rather than failed (the
classroom's return marker sits behind the door the story has not opened yet). It then
bounces between two rooms three times and asserts the node count and orphan count come back
where they started, with one location, one player and one companion in the tree throughout.
The per-location numbers it prints are quoted in
[TECHNICAL_ROADMAP.md](TECHNICAL_ROADMAP.md) (Phase 5b.3).

## 5. Not in this round

- No dialogue-panel redesign, no NPC name labels, no new character models, no story or
  dialogue rewrites, no minimap, no combat, inventory or quests, no camera or location
  rebuild, no third-party navigation addon, no wholesale rewrite of the player or of
  the interaction controller.
- No agent avoidance between moving bodies, no off-mesh links for stairs that are not
  ramps, no path smoothing, and no navigation-aware companion. Each mesh covers one
  location only, so nothing routes across a boundary.
- Where a location's own geometry was the problem, the geometry was fixed rather than
  the navigation: the courtyard's exit into the lane behind the flats ran across
  mesh-only boxes with no collider, so it is now a real mouth in the north block with a
  floor flush with the courtyard (issue #33). See
  [IMPLEMENTATION_NOTES_PLAYGROUND.md](IMPLEMENTATION_NOTES_PLAYGROUND.md) §6.

## 6. Evidence, and what it is not

Automated (headless, CI):

- `tests/navigation_test.gd` — per-location bake, the spawn on the mesh, and spawn→exit
  reachability for *every* exit rather than for one of them (an exit that only exists in
  the file is a door painted on a wall); a real walk with the physics body (arrival,
  distance travelled, no drift afterwards); refusal of off-mesh points; an unreachable
  island that is never
  climbed; a wall added between the player and the destination that is walked around
  (waypoint count and clearance measured); manual cancellation; destination
  replacement; cancellation across a location swap.
- `tests/automatic_interaction_test.gd` — click-to-talk from across the room,
  immediate activation in reach, an inspectable prop, a probe exit whose transition
  runs through the director, a target disabled mid-walk, a target freed mid-walk,
  E still working, and a ground click that moves without activating anything.
- `tests/dialogue_pointer_test.gd` — one option per click, no fall-through to the
  world (against a control case), digit keys, hover styling, layer order, and a
  language switch that re-renders the options in place.
- `tests/street_prompt_test.gd` — the new prompt key in both languages, the unchanged
  destination, the corridor's separate key, and the dismissal rewrite leaving the
  street alone.

Visual (capture workflow, scripted, not a human playtest):

- floor click → destination ring → visible movement, with the route's waypoint count
  and length logged beside the straight-line distance;
- a held movement key interrupting an automatic walk;
- a click on the timetable sheet opening its inspection;
- a click on Q from out of reach: the walk, then the conversation;
- a click on the classroom door: the transition without a key;
- a mouse-selected dialogue option in the residential stair conversation.

Both CI jobs pass on the branch head: the Godot CI job (24 headless checks, the four
new ones included) and the playthrough capture job, which reports `RESULT: the
playthrough reached the end of the built content.` and writes the frames.

The game code was red for seven rounds before that, and every failure turned out to be
a defect rather than a test to relax. The three that were invisible from reading the
code:

- a navigation region whose cell dimensions disagree with the map is refused silently,
  and the map only answers queries a frame or two after the bake — `is_routable()`
  exists because a mesh can be perfect and the map still empty;
- a headless run opens a 64×64 window, so a bottom-anchored panel is laid out above the
  top edge and a click on one of its buttons lands outside the viewport;
- the engine's source-geometry parser did not pick up the instanced prop bodies, so the
  classroom baked a floor plate with every desk left out.

The capture went red six more times with the game code untouched, and every one of those
was the capture's own brittleness:

- a step written under GitHub's `-e` threw its log away at the first non-zero exit, so a
  failure arrived as "Process completed with exit code 1" and nothing else;
- the floor-click scan reached down to 85% of the viewport height, inside the
  bottom-anchored dialogue panel, so a point picked there was a click on the panel;
- the same scan asked for floor 4–6.5 m away with no fallback, and at one classroom spot
  found none — which was then reported as "a click did not move the character";
- a clicked point can sit on visible floor the map cannot reach. The navigator builds a
  route to the nearest point it *can* reach, the character takes two steps, and the
  capture read that as a walk that did not happen;
- teleporting to a starting position can leave the capsule inside a desk. The map still
  answers, the walk starts, `move_and_slide()` has nowhere to go, and the stall watchdog
  cancels it — three attempts, each 0.00 m from where it started;
- the engine can exit non-zero under Xvfb while tearing down the window and GL context,
  after the run wrote `RESULT` and printed no failure, which failed a playthrough that
  had finished.

That last one changed what the capture job trusts. The log decides now: a `FAILURE:`
line fails the job, and so does a missing `RESULT` marker; a non-zero exit after a clean
marker is reported as a warning about teardown instead. A run that stops early still has
no marker and still fails, so the bar has not moved.

The capture has not been run on Windows, and no hands-on playtest has been performed
on any platform. The Windows checklist for a human is in the pull request.
